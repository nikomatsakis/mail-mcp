Start here

What this is, in plain words

An AI assistant has no mailbox. It cannot log in to yours, cannot see who wrote to you yesterday, and cannot send anything on your behalf. This service is the bridge — and it is already running, so there is nothing to install.

01

You point your assistant at one URL

A single command adds mail-mcp.webapace.ink/mcp as a tool provider. No download, no build, no Node.js.

02

You supply your address and an app password

They travel as two headers with each request. The service holds no accounts and stores nothing between calls.

03

The assistant gains 20 abilities

"What came in overnight", "reply to Anna", "show me the invoice she attached" — asked in normal words.

What you need before you start

  • A mailbox that speaks IMAP — which is nearly all of them. Gmail, Outlook, iCloud, Fastmail, Yandex and a dozen others are recognised from your address alone; anything else needs two host names you can copy from your provider's help page.
  • An app-specific password for that mailbox. Creating one takes a minute and is step 1 below.
  • An assistant that speaks MCP — Claude Code, Claude Desktop, Cursor and others.
One thing to weigh first. Unlike an API token scoped to one project, a mailbox password opens the whole mailbox — so on the hosted endpoint it passes through this host on every request. Nothing is stored here, and the guard rails in step 3 narrow what can be done with it, but if that trade is not acceptable to you, the same server runs on your own machine in a few commands: see Running it yourself.

Setup

Three steps, about two minutes

Create an app-specific password

Your normal password will not work: providers stopped accepting it for mail programs years ago. What you need instead is a separate password that exists only for this, and can be revoked without changing anything else.

ProviderWhere to click
Gmail / WorkspaceTurn on 2-Step Verification first, then myaccount.google.com/apppasswords. Workspace accounts also need IMAP enabled by an administrator
iCloudappleid.apple.com → Sign-In and Security → App-Specific Passwords. Your login is often just the part before @
FastmailSettings → Privacy & Security → App passwords
Yahoo / AOLAccount security → Generate app password
Yandex / Mail.ruSecurity settings → app passwords, and switch IMAP on under mail-client settings
ZohoSecurity → App passwords, plus IMAP access in Mail Settings
Outlook.com / Microsoft 365Usually OAuth only — see the note below
ProtonInstall Proton Bridge and use the login and password it shows you
Your company serverOften your normal password. Ask whoever runs it for the IMAP and SMTP host names
Microsoft is the awkward one. Personal accounts and most tenants now accept only OAuth, so no password will work. Supply an access token as the password together with X-Mail-Auth-Type: oauth2, or use a mailbox elsewhere. The same option works for Gmail if you prefer a token to an app password.

Connect your assistant

Pick the tool you use. Two values are yours to fill in: the address you sign in with and the password from the previous step.

One command in the terminal:

claude mcp add --transport http mail \
  https://mail-mcp.webapace.ink/mcp \
  --header "X-Mail-User: you@fastmail.com" \
  --header "X-Mail-Password: your-app-password"

For a recognised provider that is the whole setup — the incoming and outgoing servers are derived from your address, and the tools appear immediately. For any other mailbox, add --header "X-Mail-Imap-Host: …" and --header "X-Mail-Smtp-Host: …".

Prefer to write the configuration by hand? Create a file named .mcp.json in the root of the repository you work in — everyone who opens that repository gets the same setup. Copy this and fill in the blanks: 

{
  "mcpServers": {
    "mail": {
      "type": "http",
      "url": "https://mail-mcp.webapace.ink/mcp",
      "headers": {
        "X-Mail-User": "",
        "X-Mail-Password": "",
        "X-Mail-Imap-Host": "",
        "X-Mail-Smtp-Host": ""
      }
    }
  }
}

Four values, and only the first two are usually needed:

  • X-Mail-User — the address you sign in with. For iCloud and some company servers this is only the part before @; then add X-Mail-From with the full address.
  • X-Mail-Password — the app-specific password from step 1. This one is required; an empty string gets you No mailbox password supplied.
  • X-Mail-Imap-Host / X-Mail-Smtp-Host — leave empty for a known provider, and they are filled in from your address. Required for anything else; your provider calls them the incoming and outgoing mail server.

The same object works anywhere your client keeps MCP servers — the tabs on either side of this one are just different file names. Add "X-Mail-Read-Only": "true" to forbid every change, or "X-Mail-Allowed-Recipients": "@yourcompany.com" to limit who can be written to; both are explained under Safety.

Do not commit a real password. Keep .mcp.json out of version control, or write "X-Mail-Password": "${MAIL_PASSWORD}" — Claude Code and Cursor substitute environment variables, so the file stays shareable and the secret stays in your shell.

Open Settings → Developer → Edit config, which opens claude_desktop_config.json, and add: 

{
  "mcpServers": {
    "mail": {
      "type": "http",
      "url": "https://mail-mcp.webapace.ink/mcp",
      "headers": {
        "X-Mail-User": "you@fastmail.com",
        "X-Mail-Password": "your-app-password"
      }
    }
  }
}

Save the file and restart the app completely (quit, not just close the window).

Create .cursor/mcp.json in your project with the same shape:

{
  "mcpServers": {

Add guard rails (optional, but read this one)

A mailbox password opens the whole mailbox. These three settings narrow what the assistant may do with it, and they are enforced by the server rather than by asking nicely in a prompt.

HeaderDefaultWhat it does
X-Mail-User *—The address you sign in with. Authorization: Basic is accepted instead of this pair
X-Mail-Password *—The app-specific password from step 1
X-Mail-Imap-Hostfrom your addressIncoming server, for a mailbox with no preset. X-Mail-Imap-Port and -Secure alongside it
X-Mail-Smtp-Hostfrom your addressOutgoing server, likewise with -Port and -Secure
X-Mail-Allowed-Recipients—Mail may only go to these addresses or @domains. To, Cc and Bcc are all checked, before anything reaches the outgoing server
X-Mail-Read-Onlyfalsetrue — the assistant can read everything and change nothing
X-Mail-Allowed-Folders—Only these folders and their subfolders are reachable, for reading as well as writing
X-Mail-Default-FolderINBOXFolder used when a request does not name one
X-Mail-Fromyour userAddress in the From header, when the login is not one
X-Mail-Append-To-Senttruefalse — do not keep a copy of what was sent

Every one of these is an environment variable too, for a copy you run yourself — MAIL_READ_ONLY, MAIL_ALLOWED_RECIPIENTS and so on. The full list, including timeouts and size caps, is in .env.example and the README.

Verify

Check that it works

Ask your assistant this, exactly:

Run mail_whoamimail_whoami

A working setup logs in to both servers and answers with your address, the two host names, how many folders you have, how much of the inbox is unread, and your quota. It checks incoming and outgoing separately on purpose: a mailbox that reads perfectly can still be unable to send, and this tells you which half is broken.

If it reports that the credentials were rejected, the message names your provider and what it wants — nearly always an app-specific password where an account password was given. If the assistant says it has no such tool, the connection was not registered: check the URL ends in /mcp, that the headers are spelled exactly as above, and restart the app.

You can also check the service itself from a terminal — this needs no credentials and should answer {"status":"ok"}: 

curl https://mail-mcp.webapace.ink/health

Three things worth knowing

  • Reading does not mark as read. The assistant can go through your inbox and leave it exactly as it found it. Marking happens only when you ask for it.
  • Folder names are forgiving. Say "sent", "trash" or "archive" and the right folder is found, whatever your provider calls it — [Gmail]/Sent Mail, Отправленные or anything else.
  • Dates are forgiving too. "Since yesterday", "the last 7 days" and 2026-08-01 all work.

The interesting part

Attachments — actually opened, not just listed

An attachment lives inside the message as an encoded block, reachable only over an authenticated connection. An assistant without this server sees, at best, a filename. This one downloads the part and hands it over in the form that is actually useful.

Images

Looked at

PNG, JPEG, GIF and WebP come back as images. "What does this screenshot show?" is a question your assistant can now answer.

Text

Read

Logs, CSV, JSON, XML — handed over as text, decoded from whatever charset the sender used, including the legacy ones.

Everything else

Passed through

PDFs, spreadsheets and archives arrive intact as files the assistant can work with rather than links it cannot follow.

What it looks like

mail_read_message returns the body together with an attachment list — name, type, size, and the handle used to fetch each one: 

// mail_read_message → excerpt of the response
{
  "subject": "Q3 invoice and the screenshot",
  "from": "Anna Petrova <anna@partner.example>",
  "body": "Hi,\n\nInvoice attached, plus the screenshot…",
  "attachments": [
    { "part": "2", "filename": "invoice.pdf", "content_type": "application/pdf", "size": 48213, "inline": false },
    { "part": "3", "filename": "error.png",   "content_type": "image/png",       "size": 92104, "inline": false }
  ]
}

In practice you say "show me the screenshot" and both steps happen by themselves. The signature logos embedded in a message are marked inline, so they are never mistaken for the document you meant.

Only what is needed is downloaded. Reading a message fetches its body part alone — a message carrying a 20 MB attachment still costs a few kilobytes to read, and the attachment travels only when you ask for it. Anything above 8 MB is refused by default rather than pulled into the conversation.

Safety

Keeping it inside bounds

Email is not a read-only API with a scoped token. A mailbox password opens everything in the mailbox and can send as you. That deserves an honest answer rather than reassurance, so here is exactly what limits it.

A recipient allowlist

X-Mail-Allowed-Recipients: @yourcompany.com — mail can only be addressed to those. To, Cc and Bcc are checked together, before the message reaches the outgoing server. The one setting worth having even when everything else is open.

Read-only

X-Mail-Read-Only: true refuses every tool that would send, move, flag or delete. Searching and reading keep working completely.

A folder allowlist

X-Mail-Allowed-Folders: INBOX puts everything else out of reach, for reading as well as writing. Subfolders of a listed folder come along.

What is careful by default

Reading a messageLeaves it unread. Marking as read is a separate, explicit request
DeletingMoves to Trash. Erasing for good needs permanent and confirm together
Deleting a folderNeeds an explicit confirmation, because it takes every message in it along
The From addressFixed by your configuration. No tool argument can change who the mail appears to be from
Bulk markingCapped at 500 messages per call, so an over-broad search cannot quietly sweep the whole mailbox
Sent mailFiled in Sent as the exact bytes that were sent, so your own record matches what the recipient got

How your password is handled

  • It is not stored. Each request carries its own credentials, is served, and is discarded. There are no accounts and no database, and nothing is written to disk. Authenticated connections are held open for a few idle minutes so a burst of requests does not re-authenticate, and that is all.
  • It is used only to reach your mail server. The service makes no other outbound calls.
  • It does pass through the host, though. That is the honest cost of a hosted endpoint, and a mailbox password is not a token scoped to one project. If that is unacceptable for you or your organisation, run your own copy — it is a few commands — and nothing leaves your network.
  • Revoking is instant. Delete the app-specific password in your provider's settings and the access is gone, with no effect on your account.
  • Least privilege still applies. An app password that only permits IMAP and SMTP cannot be used to log in to the web interface or change your account.
  • What the assistant reads becomes part of your conversation with it, exactly as if you had pasted it in yourself. That is worth remembering before pointing it at a mailbox full of things you would not paste.

FAQ

Questions people actually ask

Which mail providers does this work with?

Any server that speaks IMAP, which is nearly all of them. Gmail, Outlook, Yahoo, iCloud, Fastmail, Zoho, Yandex, Mail.ru, GMX, AOL, Migadu and mailbox.org have presets, so your address alone is enough. For anything else — a company server, a small host, your own — you give the incoming and outgoing host names once.

Why does my password not work?

Because almost every provider refuses the account password over IMAP. You need an app-specific password: a separate value generated in the provider's security settings, used only here, revocable on its own. Gmail requires 2-Step Verification before the option even appears, and several providers additionally need IMAP switched on in the web interface. The error message from mail_whoami names your provider's particular requirement.

Can the assistant email anyone it likes?

Not if you set a recipient allowlist. X-Mail-Allowed-Recipients restricts outgoing mail to named addresses or whole domains, checked across To, Cc and Bcc before anything reaches the outgoing server. There is also a full read-only mode in which nothing can be sent or changed at all.

Will it mark things as read, or move things around by accident?

Reading leaves a message unread unless you explicitly ask to mark it. Deleting means moving to Trash; erasing for good needs permanent and confirm together, and deleting a folder needs a confirmation of its own.

Does my password pass through your server?

On the hosted endpoint, yes — it arrives as a header, is used to open the connection to your mail server, and is discarded. Nothing is stored: no accounts, no database, nothing on disk. But a mailbox password is not a token scoped to one project, so if that trade is not acceptable, run the same server yourself. It speaks stdio as well, started by your assistant on your own machine, and then nothing leaves your network at all.

Can it read a screenshot someone emailed me?

Yes, and that is the difference between this and a text dump of your inbox. PNG, JPEG, GIF and WebP are handed over as images the model can look at; text files arrive as text, decoded from whatever charset the sender used; anything else arrives as a file it can still work with.

Will replies thread properly?

Yes. A reply carries the In-Reply-To and References headers from the original, so it appears inside the conversation in the recipient's mail client rather than starting a new one. The original is marked as answered, as any mail client would, and your copy is filed in Sent.

Can I connect two mailboxes at once?

Yes. Add two entries with different names — for example mail-work and mail-personal. The assistant sees both sets of tools and picks by name.

My company mail server is only reachable inside the network.

Then the hosted endpoint cannot reach it, and requests for private addresses are refused on purpose. Run your own copy instead — see Running it yourself. It connects from your machine, so anything your machine can reach works, including a server on a private network or a Proton Bridge listening on localhost.

What happens with a very large mailbox?

Nothing is downloaded wholesale. Searching runs on the server's own index, listings return short summaries, and reading a message fetches only its body part. Logging in is the expensive step, so authenticated connections are kept warm for a few minutes and reused instead of re-established for every request.

Self-hosting

Running it yourself

Three cases call for your own copy: a mail server that lives only inside your network, a policy that forbids credentials passing through someone else's host, and simply preferring that a mailbox password never leaves your machine. All three are solved the same way.

As a local process

The server speaks stdio, the transport MCP clients start themselves — so nothing listens on the network at all. Configuration comes from environment variables (MAIL_USER, MAIL_PASSWORD, …) instead of headers.

As a container

The image serves the same page on / and the same MCP endpoint on /mcp at your own address. Every header on this page behaves identically, and MAIL_ALLOWED_HOSTS can pin it to your own mail servers.

Locally it is three commands and one claude mcp add:

git clone git@github.com:amalychev/mail-mcp.git
cd mail-mcp
npm install && npm run build

claude mcp add mail \
  --env MAIL_USER=you@fastmail.com \
  --env MAIL_PASSWORD=your-app-password \
  -- node /absolute/path/mail-mcp/dist/index.js

Requires Node.js 20 or newer. Everything else on this page — the tools, the folder aliases, the guard rails — works exactly the same.

Why a public endpoint refuses internal servers. Without an explicit allowlist a hosted deployment will not connect to localhost or private address ranges, so it cannot be used to probe the network it runs in. An internal mail server, or a Proton Bridge on your own machine, is therefore a job for a local install — which is the right answer anyway.
Where to look next. The repository's README.md covers both modes in full: every environment variable and its header equivalent, the provider presets, the Docker build, the deployment script, and how to add tools of your own.
